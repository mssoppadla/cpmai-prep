Operationalizing AI Models in Production — CPMAI Phase VI

From Model Evaluation to Real-World Impact · Sept 2026

GUARD-RAIL · Trustworthy AI & Model Governance in operation applies to all three lanes below — nothing ships or stays live without it

GOVERN

Who governs the live model — and what gets logged

  • Provenance & auditing (train · test · deploy)
  • Logging of model & data usage, iterations
  • Version usage · bias-measure monitoring
  • Protect model, training & inference data
  • Controls on sharing / extension by others
  • Responsible groups + response mechanism
SAFE

Safety boundaries — and what happens when they are crossed

  • Acceptable boundaries defined at the outset
  • Fallback plan if it operates outside them
  • Must not endanger humans by neglect
  • Reliable throughout its life cycle
SECURE

Securing the model, its data and who can touch it

  • Access control: who · when · where · why · how much
  • Protect model + training data + settings
  • Vulnerability analysis · report changes
  • Sanitize inputs · anonymize data
  • Secure APIs · metadata · configs · backups
THREATS

Attacks to expect — and the guardrails against them

  • Adversarial inputs · data poisoning
  • Prompt injection · jailbreaks · deepfakes
  • Prompt filtering · output moderation
  • Model constraints · content scoring
  • Red teaming before & after go-live
HUMAN

Where a human must stay in the loop · which laws apply

  • Runaway · inconsistent · ambiguous · probabilistic
  • Cyber & physical threats need human intuition
  • Disclose “you are talking to an AI”
  • NIST AI RMF · GDPR / CCPA · EU AI Act audits
DataOpskeeping the data flowing, valid and traceable
(data-engineering environment)

Managing the data life cycle after go-live

  • How data is generated, collected, stored
  • Continuous pipeline updates
  • Refresh & change-data-capture
  • Retention, deletion, archival

Ingest → validate → align schema → track lineage

  • Validate at collection (checksums, reconciliation)
  • Schema alignment & compatibility
  • Lineage: origin → transform → destination
  • Documented, version-controlled, re-executable

Three separate data pipelines: training · inference · retraining

  • Training — batch, GPU, iterative
  • Inference — real-time, lighter, may differ from training
  • Retraining — fed by production feedback
  • Never reuse one pipeline for all three

Watching production data drift away from training data

  • Training vs production distribution
  • Histograms · PSI · Kolmogorov–Smirnov
  • Causes: data change · operational change · new expectations
  • Feeds the retraining trigger (MLOps)

Securing production data & protecting privacy

  • Encryption · access controls · permissions
  • Anonymisation of PII in logs
  • Regular security & compliance audits
  • GDPR / CCPA / HIPAA obligations
MLOpskeeping the model correct, versioned and monitored
(DevOps for ML + model-specific Ops)

A model has two phases: training vs inference (serving)

  • Training: GPU-intensive, iterative, batch
  • Inference: lighter compute, no GPU, optimise for impact
  • Two phases — not build/test/deploy of apps
  • Lives in app · server · cloud · desktop · browser · edge · embedded

Version every model, data set & config — never overwrite the live model

  • Model registry; v1 kept while v2 deploys
  • Per version: training set · test/validation sets · outputs · confusion matrix · hyper-params · prompts · config
  • Any prediction traceable to model + data version
  • Hot-fix retrain over the prod file

When to retrain: on drift triggers, never on a calendar

  • Data drift · concept drift · label/target drift → model decay
  • Triggers: metric < threshold · distribution shift · KPI moves · class-balance shift
  • Retrain every N months regardless
  • Evaluate → root-cause & retrain → iterate pipeline → deploy & monitor

Model scaffolding: the code around the model that makes it usable

  • Prompt chaining · agentic frameworks · orchestration
  • External memory · JSON-schema output validation
  • Handle outputs & probabilities; format inputs
  • Needed even for third-party models
  • → hands outputs to downstream consumers (DevOps lane)

Running GenAI / LLMs in production

  • Prompt optimisation · RAG (refreshed knowledge base) · fine-tuning
  • Self-hosted vs API-hosted: control · quality · expertise · cost · moderation
  • Risks: rogue outputs · degradation · API versions/cost · adversarial prompts · less control
  • → more humans in the loop, not fewer

Monitoring the live model — every alert needs an owner and a response

  • Latency · perf time · request volume · prediction errors · accuracy / recall / F1 · user feedback
  • Usage & abuse alerts · usage matches intent
  • Tiered severity thresholds, each with a response
  • 300 unread alerts CloudWatch · Datadog · Grafana
DevOps / DevSecOpskeeping the service running, integrated and secure
(operationalization environment)

How often & how fast are predictions needed? → serving mode

  • Weekly / nightly → batch
  • Unbounded stream → streaming / stream learning
  • Request-response in budget → API / microservice
  • Offline / remote → edge
  • Cold path = accuracy · hot path = speed

Where does the model run? on-prem · cloud · edge · device

  • ☁ cloud · 🏢 on-premises · 📱 mobile · ⚙ edge (Jetson, Pi) · 🌐 browser · 🔩 embedded · MLaaS
  • Train in cloud / host on device · train local / host in cloud · both in cloud
  • Regulated + fast iteration → hybrid cloud + on-prem

One model, many sites: four architecture decisions

  • 1 Store & govern: centralized repo · decentralized
  • 2 Train / adapt: site-specific tuning · federated
  • 3 Inference: cloud-uniform · hybrid edge · hybrid on-prem · multi-cloud
  • 4 Package: containers / Kubernetes

Releasing a new model version safely (CI/CD & rollout)

  • Controlled promotion; integration tests with CRM / order systems via secure APIs
  • Load & stress test · auto-scaling
  • Deploy alongside: blue-green · canary · shadow · A/B
  • Tested rollback path before traffic shifts

Who uses the predictions & how systems connect

  • Who consumes predictions: apps · workflows · dashboards · agents · people
  • Connectors via secure APIs: CRM, order, ticketing, ERP; near-real-time sync
  • Non-AI work: application & front-end development, UI, accessibility
  • Output handling: probability → decision · confidence threshold → escalation · disclosure
  • Batch outputs → reports; real-time → in-app response

Deployment plan — decided before go-live, not during

  • Strategy & timeline · infra & resources · IT coordination
  • Checklists with validation criteria
  • User-access provisioning · security config
  • Post-deployment verification & testing

When the AI is down: fallback & business continuity

  • Fallback: prior system · limited service · manual override + escalation · human in loop
  • Incident response · backup & DR · business continuity
  • Test the contingency regularly
  • An outage is never an excuse to stop the business

DevSecOps: security built into every release

  • Same security & compliance protocols as the rest of the stack
  • Continuous integration & feedback loops
  • Automated documentation · audit trails & logs
  • Traceability: input → decision

The operations loop — repeats for the life of the model

PEOPLE & CLOSURE after go-live: users, hand-over and the next iteration — the project is not done when the model ships, it is done when operations can run it without you

Why AI projects fail after launch

  • Maintenance time & budget not planned (retrain, clean, label)
  • Consequences of drift not accounted for
  • Build, test, deploy and walk away
  • COVID-19 broke seasonality-tuned e-commerce models

Getting people to actually use it — adoption plan

  • Pilot group → phased rollout, each phase validated
  • User training & communication: what it does / does not do
  • Feedback loop into the next iteration
  • Adoption tracked as a KPI · big-bang rollout

Closing the iteration: final report & lessons learned

  • Outcomes vs Phase I criteria · realised ROI / KPIs
  • What worked, what to improve, best practices
  • Present to stakeholders & leadership

Handover to the operations team

  • Runbooks · knowledge transfer to support teams
  • Maintenance & support procedures
  • Roles & responsibilities for operations
  • Handover documentation & training

Planning the next iteration

  • Model improvement & expansion (multilingual, new features)
  • Integration & deployment enhancements
  • User-experience optimisation · escalation
  • Compliance & fairness audits · HITL refinements
