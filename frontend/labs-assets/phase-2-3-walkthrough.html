Govern & design the pipelines — decided in Phase II, enforced through Phase III

Phase II decides · Phase III enforces

These decisions are MADE in Phase II, alongside data gathering (steps 03–06 above) — this band sits at the Phase II/III border because Phase III ENFORCES them at every stage that follows. Nothing here waits for Phase III to start; by the time data moves, all of this is already decided.

Define the four pipelines — abstractly, not tied to one tool
  • Data collection / ingestion pipeline — moves raw data from sources to a staging area or lake (also called a data feed). Defined first, so the training pipeline has something to read.
  • Training pipeline — gather → clean → enhance → label → balance → split → fit transforms → training set. Built and RUN in Phase III, not just discussed — models cannot run on missing data.
  • Inference pipeline (also called production / serving pipeline) — collect → clean and format for prediction; no labels; the SAME fitted transforms as training. Planned early although used in Phase VI; production data may slightly differ in volume, velocity and technology.
  • Retraining pipeline — gather new real-world data → run the SAME full preparation again (cleanse → filter → label → split → balance) → REFIT the transforms on the new training set (never just re-apply the old ones — the new data has its own medians, categories and vocabulary) → retrain → evaluate against the live version on the locked test set → redeploy as a new version. Retraining data passes the same quality gate as the original.
Choose the pipeline mode and movement pattern
  • Batch / on-demand (the “cold path”) — runs on a schedule or trigger; quality over speed. Weekly demand-forecast refresh.
  • Real-time / streaming (the “hot path”) — must respond within an SLA. Card transactions scored in <200 ms. Trap: streaming for everything — cost and complexity without a need.
  • ETL — transform BEFORE loading, into a warehouse with a fixed schema. ELT — load the raw data into a lake FIRST, transform per project. The transform stages below are the same work in both — only their position relative to the load changes.

06

Gather, land & reconcile the data

Phase II

The data-needs definition, source inventory and source mapping happened above (steps 02–03), and the workspace and integration framework are ready (steps 04–05). This step EXECUTES those decisions — it physically gathers, lands and reconciles the data, and adds the scope and movement choices. The formal profiling (the 4 Vs), quality audit and EDA come NEXT, in step 07, on the data this step landed. Exam wording trap: inventory, audit, fact-checklist, reconciliation are Phase II assessments; cleansing, normalisation, pruning, synthetization are Phase III treatments — the phase named in the question decides which word is right.

Objective-driven scope selection
  • Temporal selection (time window) — keep only the period whose data still describes today's world; after a structural shift (crash, pandemic, new regulation) older records mislead. House-price model trained on post-2008 sales only.
  • Categorical / relevance selection — keep only segments in scope for the objective.
  • Coarse pruning at the source — dump first, prune at first selection. With our lakehouse/ELT pattern, extraction normally lands the FULL dump (all columns) into the raw snapshot — the “take the dump, then work” reality. The coarse pruning is then a REAL, explicit step — the first Phase III action, done to the landed data before any cleaning: one selection query pulls the project slice from the snapshot, applying the time window, the in-scope segments and the column drop in a single pass. The dropped fields (device serials, firmware strings, upload timestamps) stay behind in the snapshot for any future project. Push pruning INTO the extraction query itself only when cost or compliance forces it: a 2 TB image-blob column you will never use, or PII fields you have no consent to move (minimisation).
    Where exactly is this executed? The scope and pruning DECISIONS are made here (and refined by step 07’s profiling and EDA) — but the EXECUTION is the very first Phase III action: the select-per-iteration query described under “Raw immutable snapshot” below pulls the project slice out of the snapshot, after landing and reconciliation and before Cleanse. Phase II decides, Phase III executes. The cost/compliance exception is executed earlier, inside the source queries of “Execute extraction from identified sources”. The finer, remaining pruning happens later in stage 11 · Filter.
Movement — why, how, and where the processing goes
  • Reasons data moves — migration, new business processes, analytics/warehousing, application or device replacement, legacy replacement, hardware upgrades, geographic movement (GDPR: EU data stays in an EU region), compliance.
  • Movement method — integration (merge into one place) · replication (copy for availability) · CDC (move only incremental changes — preferred when data is large and changes often; a full nightly reload of a 10 TB table is the trap).
  • Move data to processing vs move processing to data — exports/APIs when data is small and stable; scripts at the endpoint when volume is huge (an edge script filters camera frames before anything transfers). The challenges of movement: cost, time, complexity, architecture impact, security, compliance.
  • Ingestion approach — batch at intervals · real-time streaming · caches/temporary stores for immediate availability.
Raw immutable snapshot + entrance quality gate
  • Raw immutable snapshot with an ingestion timestamp — store the data untouched and dated BEFORE any processing (s3://raw/orders/2026-06-30/). It is the input to lineage, backfills and audits. Trap: cleaning in place on the only copy — you can never reproduce anything again.
  • Quality gate at the entrance — automated schema validation, row counts, null rates, duplicate rate on every load; the run FAILS if, say, the null rate on customer_id exceeds 0.1% — instead of discovering the broken column after training.
  • In ELT, the transform stages below happen after this load, inside the lake.
  • The working pattern this enables: the snapshot holds EVERYTHING that was landed; each project iteration then SELECTS only the slice it needs from it — this select is where the temporal/categorical scope AND the coarse column pruning are actually applied (the finer pruning waits for the Filter stage) — the raw copy is never trimmed. So a later iteration can select a different slice without going back to the source systems, every selection is reproducible (training_set_v3 = raw snapshot + pipeline version), and at retraining a NEW snapshot is landed and the same selection logic runs again on it.

Reconcile data coming from multiple sources
  • Identify conflicts → spot mismatches (different units, timestamps, or values for the same record)
  • Resolve duplicates → remove or merge overlapping entries
  • Standardize formats → align units, naming conventions and data structures — but only as far as needed to MERGE records correctly.   • Align timelines → synchronize data collected at different times or frequencies
Why do these fixes here, when treatment is Phase III? Reconciliation is CROSS-SOURCE surgery — two systems disagreeing about the same appointment must be merged into one truthful record before a dataset even exists. Phase III cleaning is CONTENT-level, model-oriented treatment WITHIN that merged dataset (imputation, outliers, scaling). The actions sound similar, but they serve a different purpose at each stage.
07

Oversee data evaluation + EDA

Phase II

Which data does this step look at? Two levels. Profiling and the quality audit run on the FULL landed dump — they are cheap and automated (row counts, null rates, the 4 Vs), and you need them on everything to know what you actually have; the scope-selection query back in step 06 is informed BY this profiling. Deep EDA then runs on a DRAFT project slice — a sample drawn from the snapshot with the scope criteria decided in step 06 — because that approximates the data the model will actually see; findings on out-of-scope data would mislead. What EDA learns refines those criteria; the definitive project slice is then materialized by the FIRST Phase III action (the select-per-iteration query). And it stays iterative: if later work reveals the scope was wrong (say the time window cut off a whole season), you re-select a different slice from the snapshot — exactly what the select-per-iteration pattern exists for.

📋 Data profiling
  • Count: how many rows and columns each table has, and row counts per intent and per channel
  • Schema & types: every column's datatype, format, allowed values
  • Ranges & value counts: for every numeric column, record its smallest and largest value (the range); for every categorical column, count how many times each value occurs. These raw counts are the ingredients — reading meaning into them (shapes, skewness) is EDA’s job, below.
  • Missingness: nulls, empties, zeros per column — the sparse fields
  • Uniqueness & cardinality: duplicates, how many distinct values each column holds
  • Relationships: check that every key link is valid — each appointment points to a patient that actually exists — and list orphaned rows (a billing row whose appointment record is gone)
  • Freshness: last-update timestamps per source
How the three stages relate: profiling collects the raw facts — counts, ranges, missing values. EDA studies those facts and identifies the patterns. Phase III then fixes what EDA found.

Conduct EDA — document in Phase II, treat in Phase III
  • How a distribution plot is made: pick one column. For a categorical column, group the rows by value and count each group — all rows carrying the SAME value are counted together. For a numeric column, first cut the number line into small ranges called bins (0–10, 10–20, …) and count how many rows fall into each. Then draw one bar per value or bin: the X-axis holds the values (or bins), the Y-axis holds the count of rows. The finished picture shows where the data is plentiful and where it is thin.
  • From raw counts to meaning — this is where profiling’s numbers get read:
    • OTP queries per hour → a symmetric bell curve peaking at 11am → normal traffic, nothing to treat.
    • Billing amounts → most bills small, a few huge → positive (right) skew: the tail stretches to the RIGHT toward large values. (Negative (left) skew is the mirror: most values high, tail stretching LEFT toward small ones — like exam scores clustered near full marks.) Skewed features often need a log transform in stage 14 · Feature engineering.
    • Rows per intent → 80% OTP / 20% rest → an imbalance verdict → run the imbalance-vs-bias question below.
  • Analyze distributions and identify biases or gaps. Count how often each value appears — appointments per doctor, queries per language. Large imbalances become visible immediately: for example, 90% of queries in English and only 10% in Malayalam/French. Note every category that is missing entirely or clearly under-represented. These under-represented groups are also the first place fairness risk becomes visible.
  • Document every pattern you find — the EDA findings register. For each important column record the shape of its distribution (a symmetric bell curve, or skewed to one side), outliers, multicollinearity, sparse fields and the class balance. Transform (a) — Cleanse

Phase III · stateless, safe before the split

Why quality first — GIGO (garbage in, garbage out): the quality of the data in decides the quality of the model out, in training AND in inference — a pretrained vision model fed blurry production frames still fails. Cleansing is continuous, not once. Everything in this stage is stateless: fixed row by row, no learned statistics — which is exactly why it is safe before the split. Why does Cleanse run BEFORE Filter? Because dedup must precede sampling (or duplicates distort the sample’s proportions), and units/formats must agree before any threshold or stratification key can be applied.

Transform (b) — Filter: select & prune

Phase III · before the split

Filtering = selection + sampling + pruning. Horizontal = rows, vertical = columns. Sequencing: the coarse pruning at the source already happened at the start of Phase III, when the project slice was selected from the raw snapshot (or, where cost/compliance demanded, in the extraction query itself); this stage does the remaining pruning and the row sampling — after Cleanse, so sampling counts unique, comparable rows.

Vertical pruning (columns) — domain-driven
Drop attributes the model plainly does not need: IDs, timestamps, constants, metadata, obviously irrelevant fields — decided by domain knowledge, NOT by target statistics (target-driven feature selection belongs to stage 14, decided on training data only). Benefits: focus, efficiency, simplicity. Trap: keeping row keys → leaky IDs (an ID column with “99% importance”). Also called: attribute pruning · feature selection (domain type).

The labelling process:

  2. Determine the annotations — bounding boxes, segmentation, NER, audio timestamps and tone

Why the order is what it is — the four questions people ask:

  • What does “fitted” mean? The step has numbers of its own computed from the WHOLE TABLE AT ONCE — many rows together (a median, a min/max, a category-average, a vocabulary) — unlike row-level fixes, which read one row at a time. Compute those numbers from the training set only, then APPLY the very same stored numbers to validation, test and production. Every set goes through the identical recipe; none of them except train is allowed to TEACH the recipe.
  • Why deduplicate BEFORE the split? Dedup means DELETING the extra copies, so only ONE copy of each message survives — and that one copy can only land in one set. Done after the split, the copies are already sitting in both train and test, and the model gets “asked in the exam what it memorized in class” → inflated score.
  • Why impute AFTER the split? Filling a missing value needs a fill VALUE (say, the median age), and the median is learned from the rows you compute it on. Compute it on ALL rows and it silently contains the test rows’ information — a whisper of the exam paper inside the study notes. Concretely: median(all 100 rows) = 34, median(train 80 rows) = 31 — training with 34 means the model was tuned using test-set knowledge, so its test score looks better than production ever will. Correct way: compute the median on train, STORE it, reuse that stored value for validation, test and production.
  • Why is a vocabulary “fitted”? Building a text vocabulary (TF-IDF, a tokenizer’s word-list) means reading the WHOLE corpus to list the known words and score how rare each is; that reading is the learning, so the vocabulary and scores are built from the training corpus only, then reused for validation, test and production text.
Why we split, the train / validation / test ratios, and the rule that follows

Training ~70% · validation · test 15–20% (guidance, not law). Train = the model learns; validation = tune and detect over/underfit; test = one final unseen judgement. Why split at all: prove it works on NEW data — never test on the data you trained on. After this line, everything is fitted on the training set only.

Pipeline sequencing: EDA → cleaning → SPLIT → transformation. Split into train/validation/test before fitting any scaler — fit scalers on the training set only, then apply to validation/test, to avoid leakage. Exclude categorical variables or already-bounded values (percentages, binary flags) from scaling decisions here.

Where does SAMPLING fit? (it happens at three different moments)
  • 1 · While defining & collecting (Phase II, step 02): stratified sampling decides WHAT to collect — ≥20k OTP queries stratified by channel (SMS, app, web), ≥500 per FAQ category.
  • 2 · At split time (here): a stratified split keeps each subset's intent mix identical to the whole — otherwise a rare intent could end up missing from the test set.
  • 3 · After the split, on train only: oversampling / undersampling / SMOTE to rebalance classes for training. Never resample validation or test — they must stay an honest mirror of reality.

Transform (d) — Feature engineering

Phase III · FIT on train, APPLY elsewhere
Fit → learn parameters from the training data
Transform / Apply → use those learned parameters to transform data

Almost every step here is stateful — its parameters are computed from the ENTIRE training dataset at once (a fill value, an outlier fence, a category list, a scaler’s mean and standard deviation, a vocabulary) — not from any single row.

So each of them is fitted on training, applied to validation, test and production with the training parameters, REFITTED at retraining.

Distinction to note: row-wise derived features (stateless) — ratios, date parts, interactions — read a single row, learn nothing, and may therefore run before the split.

Outlier treatment — six steps, in order
  1. Profile the column — inspect the Age column’s distribution with a histogram to spot potential outliers.
  2. Define the outlier criteria — choose a rule such as IQR (below Q1 − 1.5×IQR or above Q3 + 1.5×IQR) or a z-score threshold (e.g. |z| > 3) to flag extreme values.
  3. Detect the outliers — apply the chosen rule to the TRAINING set’s Age column and mark the rows that fall outside the acceptable range.
  4. Identify the cause, then decide the treatment — investigate first: is it a real value or an error? An age above 200 is an error → correct it or treat it as missing. A real but extreme value → cap it at the threshold (winsorize), remove the row, or replace it with the median/mean, depending on the business context. A real and MEANINGFUL extreme (fraud!) → keep it and use robust models; never silently delete rare real events.
  5. Apply the transformation — execute the chosen treatment on the training set only, then store the parameters (caps, thresholds) for reuse.
  6. Reuse the parameters — apply the same thresholds or caps to the validation and test sets WITHOUT refitting, so the sets stay consistent and nothing leaks.
Scaling the numeric features — normalisation vs standardisation, fitted on train

Same word, two meanings — placed where each belongs in a real project: stage 10 · Cleanse did “format standardisation” — text/format hygiene (dates, units, casing), row-level, before the split. THIS step is statistical rescaling of numbers, and runs AFTER the split because the scaler is learned from data (fit on train only). One more sequencing note: scaling and encoding are siblings, not a sequence — scaling rescales the NUMERIC columns, encoding converts the CATEGORICAL columns into numbers; both are fitted on train after the split, and it does not matter which of the two you run first.

  • Normalization (min-max scaling, values → [0,1]): for distance-based models (KNN, SVM, neural nets)
  • Standardization (z-score, mean = 0, variance = 1): for distribution-based models (linear/logistic regression, PCA)
  • Store fitted parameters (min, max, mean, std) from the training set; apply consistently across all subsets
  • Validation: check transformed distributions (histograms, boxplots); ensure scaling doesn't distort feature relationships; confirm no leakage (test set untouched during fitting)
  • Reproducibility & documentation: log scaler parameters · version-control transformations (MLflow, DVC, Git) · document which features were scaled, why, and how · ensure transformations are repeatable in production pipelines

Why this matters
  • Memory: 20,000 pincodes one-hot = 20,000 columns of mostly zeros — RAM and storage drain for no signal.
  • Speed: every extra column slows training and inference.
  • Overfitting: a pincode seen 3 times gets its own column and the model memorizes those 3 rows instead of learning.
  • Accuracy: and yes — sparsity and the curse of dimensionality rise TOGETHER: every mostly-zero column one-hot adds is another dimension across which the same rows are spread thinner, so patterns dissolve and performance degrades. That coupling is exactly why one-hot on 20,000 pincodes hurts.
  • The fix in one line: target encoding keeps ONE dense, informative column; the cross-validation wrapper is what stops it peeking at the answer (leakage).
Encoding traps the course tests
  • One-hot for linear models: drop one column (drop="first") to avoid perfect multicollinearity.
  • Frequency/count encoding: counts must come from the TRAINING set — counts on the whole dataset leak test frequencies in.
  • Target/mean encoding: must be out-of-fold and smoothed — without OOF and smoothing on tiny categories the leakage is extreme.

Transform (e) — Balance & enlarge

Phase III · training set ONLY

Everything in this stage touches the training set only — validation, test and production rows stay real. And yes, that means exactly what it says: synthetic or augmented rows are NEVER placed in validation or test. Those two sets exist to measure how the model performs on reality — put generated rows in them and you are grading the model on your generator’s imagination, not on the world. An exam option that resamples or augments validation/test is always wrong.

Why this stage comes after feature engineering: SMOTE and its relatives create new rows by drawing lines between existing rows in feature space — they need numeric, gap-free, scaled columns, so encoding, imputation and scaling (stage 14) run first, and the resampler is refitted inside every training run. Plain random over- or under-sampling only copies or deletes whole rows and may run earlier.

Resampling — change the class distribution (training set only)

Sampling adjusts the ROW COUNTS of the training set to fix severe class imbalance — unlike splitting rules (which rearrange boundaries), it creates or deletes data points so the model can learn rare classes. Whatever the technique, only the training set is sampled.
