Gather required data & reconcile

Phase II

  • Pull from internal databases, warehouses, external APIs
  • Identify patient, billing, prescription tables
  • Use secure connectors (ODBC/JDBC, API calls)
  • Decide structured formats (CSV, JSON, Parquet)

Coordinate transfers and migrations to AI environments
  • Set up a staging area in cloud or local servers
  • ETL pipelines (Airflow, Azure Data Factory, …)
  • Anonymize data
  • Encrypt in transit & at rest (ABDM, India's Data Protection Bill)
  • Document schema transformations
Implement collection processes for ongoing feeds
  • Enable continuous ingestion for new patient queries
  • Connect chatbot logs and WhatsApp transcripts
  • Schedule batch jobs or streaming pipelines
  • Normalize multilingual inputs (English + local languages)
  • Store in incremental datasets
Validate completeness and accuracy during collection
  • Check record counts against source systems
  • Validate field accuracy (dates, doctor names, billing amounts)
  • Run schema-validation scripts
  • Flag and correct transfer anomalies — problems created by the COPY itself: rows lost or duplicated during transfer, truncated or garbled records, the same batch loaded twice, schema drift between source and landing zone. This step asks “did the data arrive intact?”. Cleaning the CONTENT (typos, missing values, outliers) is a different job and happens once, in stage 13 · Cleanse.
  • Validate the relationships (primary/foreign keys)
Establish data refresh and update procedures
  • Define refresh frequency (daily for appointments, weekly for billing)
  • Automate incremental updates (CDC)
  • Archive old data for audit
  • Monitor for schema changes and update mappings
  • Keep existing data clean, current, compliant
Reconcile data coming from multiple sources
  • Identify conflicts → spot mismatches (different units, timestamps, or values for the same record)
  • Resolve duplicates → remove or merge overlapping entries
  • Standardize formats → align units, naming conventions and data structures — but only as far as needed to MERGE records correctly. A join cannot happen while one system writes “MRN-0012” and the other writes “12”, or one stores weight in kg and the other in lbs. Full content standardization for modeling still happens once, in stage 13 · Cleanse.
  • Define the authoritative source → decide which source to trust when values differ
  • Align timelines → synchronize data collected at different times or frequencies
Why do these fixes here, when treatment is Phase III? Reconciliation is CROSS-SOURCE surgery — two systems disagreeing about the same appointment must be merged into one truthful record before a dataset even exists. Phase III cleaning is CONTENT-level, model-oriented treatment WITHIN that merged dataset (imputation, outliers, scaling). The actions sound similar, but they serve a different purpose at each stage.
07

Oversee data evaluation + EDA

Phase II
📋 Data profiling
  • Count: how many rows and columns each table has, and row counts per intent and per channel
  • Schema & types: every column's datatype, format, allowed values
  • Ranges & value counts: for every numeric column, record its smallest and largest value (the range); for every categorical column, count how many times each value occurs. These raw counts are the ingredients — reading meaning into them (shapes, skewness) is EDA’s job, below.
  • Missingness: nulls, empties, zeros per column — the sparse fields
  • Uniqueness & cardinality: duplicates, how many distinct values each column holds
  • Relationships: check that every key link is valid — each appointment points to a patient that actually exists — and list orphaned rows (a billing row whose appointment record is gone)
  • Freshness: last-update timestamps per source
How the three stages relate: profiling collects the raw facts — counts, ranges, missing values. EDA studies those facts and identifies the patterns. Phase III then fixes what EDA found.
Assess quality dimensions (accuracy, completeness, consistency, timeliness, relevance, trustworthiness)
Measure them with reconciliation counts, checksums and cross-channel comparisons. EXAMPLE In the appointment database, check that at least 98% of records carry a valid patient ID and timestamp.
Assess labeling needs (supervised learning check — feeds Gate 1)
  • Is labeling needed at all? Supervised learning needs an answer column. Do the labels already exist naturally (repaid/defaulted comes free from billing history), or must humans create them (intent tags on chat messages)?
  • If humans must label: run a small PILOT — annotate ~500 sample rows, measure how often labelers agree, and confirm a rulebook is writable.
  • Feed the answer into Gate 1: label availability, pilot agreement rate, and estimated labeling cost/time are part of “does the data meet solution needs”. The full labeling campaign itself stays in Phase III (stage 15 · Label) — after the gate approves spending on it.
Evaluate freshness and relevance
Check the last-update timestamp of every source. EXAMPLE Insurance codes update monthly, so a 6-month-old copy is stale. Also confirm the data still reflects current clinic workflows — new doctors, new lab tests.
Review schema and structure for modeling compatibility
Align field names, formats and datatypes across sources so tables can be joined and modeled. EXAMPLE The appointment database says “Doctor_Name” while billing says “Physician_ID” — map them to one consistent field.
Conduct EDA — document in Phase II, treat in Phase III
  • How a distribution plot is made: pick one column. For a categorical column, group the rows by value and count each group — all rows carrying the SAME value are counted together. For a numeric column, first cut the number line into small ranges called bins (0–10, 10–20, …) and count how many rows fall into each. Then draw one bar per value or bin: the X-axis holds the values (or bins), the Y-axis holds the count of rows. The finished picture shows where the data is plentiful and where it is thin.
  • From raw counts to meaning — this is where profiling’s numbers get read:
    • OTP queries per hour → a symmetric bell curve peaking at 11am → normal traffic, nothing to treat.
    • Billing amounts → most bills small, a few huge → positive (right) skew: the tail stretches to the RIGHT toward large values. (Negative (left) skew is the mirror: most values high, tail stretching LEFT toward small ones — like exam scores clustered near full marks.) Skewed features often need a log transform in stage 18 · Feature engineering.
    • Rows per intent → 80% OTP / 20% rest → an imbalance verdict → run the imbalance-vs-bias question below.
  • Analyze distributions and identify biases or gaps. Count how often each value appears — appointments per doctor, queries per language. Large imbalances become visible immediately: for example, 90% of queries in English and only 10% in Malayalam/French. Note every category that is missing entirely or clearly under-represented. These under-represented groups are also the first place fairness risk becomes visible.
  • Document every pattern you find. For each important column, record: the shape of its distribution — is it a symmetric bell curve, or is it skewed (skewness means the shape leans away from that symmetric bell curve to one side)? Also record outliers, multicollinearity (two features that rise and fall together, such as website traffic and page views), sparse or thinly-populated fields (many missing, null, empty or zero cells), and the class balance between intents. Against each finding, write the planned correction — the fixing itself happens in Phase III.
  • Class imbalance rule: target class 1 has 80% of the data, target class 2 has 20%. If that IS the real-world representation → not bias; fix the imbalance with oversampling, undersampling, SMOTE. If it's missed or wrongly labelled/captured prod data → it's a bias → go and get it, or give a proper instruction manual to label it properly.
  • Ensure categorical-variable encoding decisions are made properly (target encoding for high-cardinality fields) . This decision travels across the journey: here in Phase II (step 07 · EDA) you simply NOTE which columns will need special encoding; in stage 18 · Feature engineering the method is chosen per column and applied — once.
  • Where each finding gets fixed (documented once here, fixed once there): skewness → stage 18 · Feature engineering (scaling/log transform) · outliers → stage 18 (treatment ladder) · class imbalance → stage 17 · Balance (resampling, train only) · encoding decisions → stage 18 · fairness/subgroup gaps → stages 13–18 (collect & label properly), PROVEN at Gate 2
  • Analytics vs data science — keep them apart, with examples: Analytics is the OUTPUT — answers from data, at four levels: descriptive (what happened — “4,200 appointments last month, 9% no-shows”), diagnostic (why — “no-shows spike on heavy-rain days”), predictive (what will happen — “these 120 appointments next week are likely to be missed”), prescriptive/projective (what should we do — “send reminders + easy reschedule links to those 120”). Data science is the DISCIPLINE that produces those answers: it translates the business need “reduce no-shows” into mathematics, forms a hypothesis (“rain increases no-shows”), tests it statistically, and builds the models behind the predictive, prescriptive and diagnostic tiers. AI/ML are advanced forms of analytics built with data-science skills — our chatbot’s intent classifier is exactly that.

GATE 1 · Determine if data meets solution needs

Decision gate
Compare available data against requirements
Line up every intent against its data target from step 02 and mark it met or not:
  • OTP Query — 21,400 collected / 20,000 required ✓
  • FAQ — 52,300 / 50,000 ✓
  • Scheduling Appointment — 8,900 / 10,000 ✗
  • Fraud Reporting — 0 / 5,000 ✗ — a coverage hole: the intent exists in the design but no data exists for it
Coverage = intents meeting their target ÷ all intents (here 2 of 4).
Assess sufficiency for robust models
Run three checks together: the 4V check (volume, variety, velocity, veracity), representativeness (including freshness and relevance), and class balance. Then apply the Goldilocks principle — aim for just-enough data, because every extra feature spreads the information across more combinations and demands more rows; taken too far this becomes the curse of dimensionality. Four more questions decide how much data is enough:
  • Which AI pattern(s) you implement — Recognition or Conversation needs LESS data than Autonomous systems or Hyperpersonalization; check against the scenario coverage & use cases
  • Build from scratch or extend a pretrained model — and how often does the data change?
  • How big or complex a model you are building — algorithm choice also drives data needs: deep networks and transformers need far more data than simpler models
  • How accurate the model must be — higher accuracy targets demand more data
Identify gaps and remediation strategies
List every category that is missing or under-represented — for example, Malayalam/French queries — and write a remediation plan for each: what will be collected, by whom, and by when.
Validate representativeness for target use cases
Data must reflect real clinic scenarios: languages spoken by patients · appointment types (consultation, lab, pharmacy) · billing categories (consultation, lab test, pharmacy).

What each scorecard line means (they sound similar — they are not)
  • Coverage vs intents — do we HAVE data for every intent at all? (Fraud Reporting with zero rows = a coverage hole.) A yes/no existence check per use case.
  • Representativeness — within the data we have, does the MIX mirror reality? Languages spoken, appointment types, billing categories in real-world proportions. You can have full coverage yet a warped mix.
  • Class balance (intent distribution) — the proportion BETWEEN the intents themselves (80% OTP / 20% everything else). Feeds the imbalance-vs-bias question from EDA.
  • Gaps & remediation — the “2 open” are: ① Malayalam/French queries under-represented (remediation: collect via branch kiosk + targeted sampling) · ② Fraud-intent scenario coverage at 45 of 60 required (remediation: author the missing negative scenarios). Each gap gets an owner and a date — that's what “remediation” means here.

Govern & design the pipelines

Phase II decides · Phase III enforces

This design work BEGINS in Phase II, alongside data gathering (steps 03–06 above), and is enforced throughout Phase III — it is cross-cutting and shapes every later stage. Nothing here waits for Phase III to start.

Define the four pipelines — abstractly, not tied to one tool
  • Data collection / ingestion pipeline — moves raw data from sources to a staging area or lake (also called a data feed). Defined first, so the training pipeline has something to read.
  • Training pipeline — gather → clean → enhance → label → balance → split → fit transforms → training set. Built and RUN in Phase III, not just discussed — models cannot run on missing data.
  • Inference pipeline (also called production / serving pipeline) — collect → clean and format for prediction; no labels; the SAME fitted transforms as training. Planned early although used in Phase VI; production data may slightly differ in volume, velocity and technology.
  • Retraining pipeline — gather new real-world data → apply the training transforms → retrain → evaluate against the live version → redeploy as a new version.
Choose the pipeline mode and movement pattern
  • Batch / on-demand (the “cold path”) — runs on a schedule or trigger; quality over speed. Weekly demand-forecast refresh.
  • Real-time / streaming (the “hot path”) — must respond within an SLA. Card transactions scored in <200 ms. Trap: streaming for everything — cost and complexity without a need.
  • ETL — transform BEFORE loading, into a warehouse with a fixed schema. ELT — load the raw data into a lake FIRST, transform per project. The transform stages below are the same work in both — only their position relative to the load changes.
Engineering guardrails
  • Ingestion idempotency — running the pipeline twice yields the same state, no duplicates (UPSERT, overwrite partitions, strict primary keys). Trap: a restart after failure duplicates millions of rows → later “deduplication” work and leakage.
  • Schema evolution / validation — detect renamed columns, new categories, changed types at the pipeline's entrance; fail the run instead of silently nulling a column (silent nulls train a broken model).
  • Stateful vs stateless transformations — the design decision behind this whole page: stateless = row by row (parse a date); stateful = needs whole-dataset statistics (a scaler, an encoder) and must be FITTED on training only, in stage 18.
  • Late-arriving data handling — events that arrive hours or days late: watermarks, immutable event logs with ingestion timestamps.
Data governance — Phase II decides, Phase III enforces
  • Trustworthy-AI plan for preparation — decide up front how representation is checked per group, how every step is documented, when audits run.
  • The nine governance areas — document & content management (unstructured files: contracts, scans, emails, images) · metadata · data quality · data architecture · data development · data operations · data security · reference & master data · data warehousing & BI.
  • The risks governance addresses — security · privacy · uptime/availability · change management · data quality · ownership/IP · provenance · auditing of changes.
  • Versioning — version the raw snapshot, the pipeline code and the produced training set: training_set_v3 = raw_2026-06-30 + pipeline v1.4. Without it you cannot answer “which data trained which model” in an audit.

Extract — Phase II decided, Phase III runs

Phase III · stage 1

The inventory, audit, profiling (the 4 Vs) and source mapping all happened above in Phase II (steps 03, 06, 07). This stage EXECUTES those decisions — and adds the scope and movement choices. Exam wording trap: inventory, audit, fact-checklist, reconciliation are Phase II assessments; cleansing, normalisation, pruning, synthetization are Phase III treatments — the phase named in the question decides which word is right.

Objective-driven scope selection
  • Temporal selection (time window) — keep only the period whose data still describes today's world; after a structural shift (crash, pandemic, new regulation) older records mislead. House-price model trained on post-2008 sales only.
  • Categorical / relevance selection — keep only segments in scope for the objective.
Movement — why, how, and where the processing goes
  • Reasons data moves — migration, new business processes, analytics/warehousing, application or device replacement, legacy replacement, hardware upgrades, geographic movement (GDPR: EU data stays in an EU region), compliance.
  • Movement method — integration (merge into one place) · replication (copy for availability) · CDC (move only incremental changes — preferred when data is large and changes often; a full nightly reload of a 10 TB table is the trap).
  • Move data to processing vs move processing to data — exports/APIs when data is small and stable; scripts at the endpoint when volume is huge (an edge script filters camera frames before anything transfers). The challenges of movement: cost, time, complexity, architecture impact, security, compliance.
  • Ingestion approach — batch at intervals · real-time streaming · caches/temporary stores for immediate availability.

Load — land & snapshot the raw data

Phase III · stage 2
Raw immutable snapshot + entrance quality gate
  • Raw immutable snapshot with an ingestion timestamp — store the data untouched and dated BEFORE any processing (s3://raw/orders/2026-06-30/). It is the input to lineage, backfills and audits. Trap: cleaning in place on the only copy — you can never reproduce anything again.
  • Quality gate at the entrance — automated schema validation, row counts, null rates, duplicate rate on every load; the run FAILS if, say, the null rate on customer_id exceeds 0.1% — instead of discovering the broken column after training.
  • In ELT, the transform stages below happen after this load, inside the lake.
13

Transform (a) — Cleanse

Phase III · stage 3 — stateless, safe before the split

Why quality first — GIGO (garbage in, garbage out): the quality of the data in decides the quality of the model out, in training AND in inference — a pretrained vision model fed blurry production frames still fails. Cleansing is continuous, not once. Everything in this stage is stateless: fixed row by row, no learned statistics — which is exactly why it is safe before the split.

Cleansing — the row-level, human-readable fixes
Row-level hygiene (safe BEFORE the split; each fix reads only its own row):
  • Remove duplicates (must be before the split — see stage 16 · Split; and done on readable raw text, BEFORE tokenization — two messages that are obvious duplicates as sentences may look different once chopped into tokens)
  • Correct inconsistent formats (dates, units, categorical labels) — also called format standardization; this is text/format hygiene, a different thing from stage 18’s statistical standardization (z-score rescaling of numbers). This is also the Phase-III treatment of the “consistency” dimension measured in Phase II (step 07 · EDA).
  • Basic consistency transformations (lowercasing text, standardizing date formats)
  • Anonymisation & generalization — mask PII, group ages into ranges; and be precise about the three levels: anonymisation (irreversible) · pseudonymisation (reversible with a key) · masking (display only). Best practice: anonymise anything the model does not need. Trap: leaving PII in “just the training set”.
  • Noise reduction & disambiguation — strip what carries no signal (background from product photos, hum from call audio) and make ambiguous values unambiguous (“NY” vs “New York” unified). Trap: noise learnt as signal → overfitting.
  • Data minimisation — keep only the fields the pattern needs (a trustworthy-AI requirement): the fraud model keeps amount, merchant and time — not the cardholder name. It overlaps vertical pruning (stage 14 · Filter): minimisation is the PRIVACY reason, pruning is the MODELLING reason.
  • Value normalisation — put values from different sources on one unit or scale before merging (sensor A in °F, sensor B in °C → one unit). Stateless, done here — NOT the min-max feature scaling of stage 18 (see the name-clash clinic).

Where did tokenization go? Not here. Text stays human-readable all the way through cleansing, filtering and labelling — the people working the pipeline need to read it. Tokenization (chopping text into model-ready pieces) happens at stage 18 · Feature engineering, inside vectorisation, just before the data goes to training.

Transform (b) — Filter: select & prune

Phase III · stage 4 — before the split

Filtering = selection + sampling + pruning. Horizontal = rows, vertical = columns.

Vertical pruning (columns) — domain-driven
Drop attributes the model plainly does not need: IDs, timestamps, constants, metadata, obviously irrelevant fields — decided by domain knowledge, NOT by target statistics (target-driven feature selection belongs to stage 18, decided on training data only). Benefits: focus, efficiency, simplicity. Trap: keeping row keys → leaky IDs (an ID column with “99% importance”). Also called: attribute pruning · feature selection (domain type).
Horizontal pruning (rows) = sampling
  • Simple random sampling — uniform random subset when ALL data is relevant but there is too much of it (10 M rows → 100 K for rapid iteration). Trap: taking the first million sorted records is NOT a sample — it's bias.
  • Stratified sampling — every sub-population keeps its share (every district represented in proportion). Note the clash: stratified SAMPLING decides size here; stratified SPLITTING (stage 16) keeps the class mix per set.
  • Cluster sampling — pick whole groups (whole clinics), then sample inside; cheaper for field collection.
  • Run the representativeness / bias check per demographic group — and note it is NOT a one-time check: first in Phase II EDA (step 07), again HERE after sampling, again after the split (stage 16 — do the sets still mirror each other?), again at Gate 2 (stage 20, with PSI/KS numbers), and continuously in production (stage 21). The trustworthy-AI plan from stage 10 defines how.

Transform (c) — Label

Phase III · stage 5 — before the split, so strata exist

The labeling NEEDS were assessed in Phase II (step 07) and priced into Gate 1; the campaign runs here — and it runs BEFORE the split so that stratified splitting has classes to stratify on. Vocabulary: a label is the class or value; an annotation is richer context (boxes, polygons, entities, timestamps). Inference data is NEVER labelled — assuming it must be is an exam trap.

Choose the labelling workforce deliberately: internal staff · outsourcing · agency · crowdsourcing · active learning (machine & human). Crowdsourcing is usually rejected on quality grounds. Synthetic data must be controlled, archived and vetted.

Where labels come from — the full sourcing menu (one list with the workforce options above)
  • Repurpose existing data — the cheapest first option: categories the business already recorded (support tickets already tagged by team). Trap: ignoring labels you already own.
  • Pre-labelled public / vendor datasets — for common tasks (objects, sentiment). Trap: licence, bias and fit not checked.
  • Crowdsourcing from users inside the product — CAPTCHA-style “select all stop signs”; works for simple labels at scale (distinct from paid crowdsourcing, which is usually rejected on quality grounds).
  • Model / GenAI pre-labelling — a model proposes labels, humans verify (the active-learning pattern from the workforce card).
Annotation types & the seven-step labelling process
  • Annotation types — class label · bounding box · polygon/segmentation · key points · NER · audio timestamps. Choose the annotation that matches what the model must OUTPUT. If the model only says WHAT is in the image (“a dog”), a class label is enough. If it must say WHERE the dog is, draw a bounding box. If it must trace the dog’s exact outline pixel by pixel, use a polygon. On taxonomy size: the ~10 tags figure is course guidance, not a law — each organisation defines its own taxonomy by need. The principle behind the number is real though: every extra tag needs its own training examples and scenario coverage, and multiplies dimensionality — so keep the tag set as small as the use case allows, and if you genuinely need many, structure them as a hierarchy (vehicle → car → SUV) rather than one flat list.
  • Sensor fusion — correlate several sensors (lidar, radar, cameras) into 3D point clouds BEFORE labelling obstacles; labelling one stream in isolation is the trap.
  • The seven-step process — gather gold-standard data → define annotations/taxonomy (≤10 tags) → human in the loop → QA/consensus — accept a label when 2 of 3 annotators agree. Agreement example: “I didn’t receive my code” — both officers mark OTP Query → accepted. Disagreement example: “my payment failed while I was waiting for the OTP” — one officer marks OTP Query, the other Fraud Reporting → a third annotator adjudicates using the rulebook, and the rulebook gains a clarifying rule so the next such message is unambiguous → train & test → use verified labels → monitor label quality. Bad labels on good images = bad data (GIGO).

Legend (from the master deck): fit = statistics learned here · apply = training parameters re-used, never re-learned · never = rows stay real · same = stateless, applied identically everywhere.

Training ~70% · validation · test 15–20% (guidance, not law). Train = the model learns; validation = tune and detect over/underfit; test = one final unseen judgement. Why split at all: prove it works on NEW data — never test on the data you trained on. After this line, everything is fitted on the training set only.

Pipeline sequencing: EDA → cleaning → SPLIT → transformation. Split into train/validation/test before fitting any scaler — fit scalers on the training set only, then apply to validation/test, to avoid leakage. Exclude categorical variables or already-bounded values (percentages, binary flags) from scaling decisions here.

What comes BEFORE the split, what comes AFTER — the exact order
  • ✅ BEFORE the split (safe — each of these looks at one row at a time, or removes rows entirely):
    • Deduplicate. Why before? Dedup means DELETING the extra copies, so only ONE copy of each message survives — and that one copy can only land in one set. Done after the split, the copies are already sitting in both train and test, and the model gets “asked in the exam what it memorized in class” → inflated score. Your worry is exactly right for keeping duplicates — the fix is that we don't keep them.
    • Row-level cleaning: fix formats, lowercase, tokenize — uses only that row's own content.
    • Row-level feature derivations: ratios, days-since-discharge, text features from the row itself.
  • ✂️ THE SPLIT — train / validation / test (stratified, so every subset keeps the same intent mix).
  • 🔒 AFTER the split — anything LEARNED from data, fitted on TRAIN only. In plain words: “fitted” means the step has numbers of its own computed from the WHOLE TABLE AT ONCE — many rows together (a median, a min/max, a category-average, a vocabulary) — unlike row-level fixes, which read one row at a time. Compute those numbers from the training set only — then APPLY the very same stored numbers to validation, test, and production. Every set goes through the identical recipe; none of them except train is allowed to TEACH the recipe.
    • Imputation — why not before? Filling a missing value needs a fill VALUE (say, the median age). The median is learned from the rows you compute it on. Compute it on ALL rows and it silently contains the test rows' information — a whisper of the exam paper inside the study notes. Concretely: median(all 100 rows) = 34, median(train 80 rows) = 31 — training with 34 means the model was tuned using test-set knowledge, so its test score looks better than production ever will. Correct way: compute the median on train, STORE it, and reuse that same stored value to fill validation, test, and production.
    • Scalers (min-max, z-score) — fitted on train, applied everywhere.
    • Target encoding — after the split AND inside cross-validation.
    • Vocabulary / TF-IDF — building a text vocabulary means reading the WHOLE corpus to list the known words and score how rare each is; that reading is the “learning”, so the vocabulary and scores are built from the training corpus only, then reused for validation, test and production text.
    • Augmentation & synthetic rows — training set only; validation/test stay untouched.
Where does SAMPLING fit? (it happens at three different moments)
  • 1 · While defining & collecting (Phase II, step 02): stratified sampling decides WHAT to collect — ≥20k OTP queries stratified by channel (SMS, app, web), ≥500 per FAQ category.
  • 2 · At split time (here): a stratified split keeps each subset's intent mix identical to the whole — otherwise a rare intent could end up missing from the test set.
  • 3 · After the split, on train only: oversampling / undersampling / SMOTE to rebalance classes for training. Never resample validation or test — they must stay an honest mirror of reality.

Split strategies — choose by the data's structure
  • Random split — shuffle and cut. Legitimate ONLY when rows are independent, balanced, with no time or group structure; on anything else it is the most common cause of leakage.
  • Stratified split — each set keeps the class proportions (fraud 0.2% in train, validation and test alike); bin continuous targets first. Clash: stratified SPLIT preserves the distribution; RESAMPLING (stage 17) changes it.
  • Temporal / time-series split — train on the past, test on the future (train ≤2025, test 2026); anything else is look-ahead leakage.
  • Group split — all rows of one patient/customer stay in ONE set, or the model memorizes people instead of patterns.
  • Spatial split — geographic hold-outs for location-dependent data.
  • k-fold cross-validation — rotates INSIDE the training portion for tuning; the test set stays locked.

Transform (d) — Balance & enlarge

Phase III · stage 7 — training set ONLY

Everything in this stage touches the training set only — validation, test and production rows stay real. And yes, that means exactly what it says: synthetic or augmented rows are NEVER placed in validation or test. Those two sets exist to measure how the model performs on reality — put generated rows in them and you are grading the model on your generator’s imagination, not on the world. An exam option that resamples or augments validation/test is always wrong.

Resampling — change the class distribution (training only)
  • Random oversampling — clone minority rows exactly until classes balance; deliberate DUPLICATION (not multiplication, which transforms). Trap: the model memorises the copies → overfitting.
  • SMOTE — draw lines between rare points and create new rows along them; preferred over random oversampling because it makes variations, not copies. SMOTE is synthetic data at ROW level; “synthetic data” below is dataset level.
  • Random undersampling — delete majority rows; only when the majority class is massively bloated (1 B non-fraud rows → 10 M). Trap: information loss.
  • Tomek links / cluster undersampling — boundary cleaning: remove majority rows sitting dangerously close to minority rows, before oversampling.
  • Class weights — the no-resampling alternative: keep the data as-is and tell the model a missed rare case costs more (our “cost setting” from the bias story).
Multiplication — make MORE rows by transforming existing ones (training only)
Three words that get swapped — pin them down once:
WordWhat it makesExample
DuplicationIDENTICAL copies of a rowRandom oversampling clones a fraud row exactly
MultiplicationTRANSFORMED copies — altered but still valid and correctly labelled (so it is a form of augmentation, never plain copy-paste)The same cat photo rotated 10°, flipped, cropped — 1,000 images become 100–200 K
SynthetizationBRAND-NEW rows generated from learned patternsA GAN invents a patient that never existed
Course chain: data transformation (alter, keep validity) → data augmentation (create additional points) → data multiplication (the techniques).
  • Images: rotation · flipping · scaling · colorization · cropping · translation · occlusion — each altered image stays valid and correctly labelled; consider the relevance of every transformation (recolouring a stop sign breaks meaning).
  • Text / audio: synonym replacement · back-translation · paraphrasing · noise, pitch and speed shifts. Trap: a synonym that flips the label (sentiment).
Choose augmentation techniques
  • Text: paraphrasing, synonym replacement, back-translation
  • Images: rotation, flipping, noise injection
  • Tabular: jittering values, bootstrapping
Generate synthetic data
  • GANs or VAEs for realistic samples
  • Simulate sensor logs or patient vitals
  • Rule-based generation for structured fields
Validate quality
  • Ensure augmented/synthetic data is realistic and unbiased
  • Compare its distributions with the original data
  • Run a domain-expert review (e.g., clinicians)
  • Check for artifacts or unrealistic patterns — a generated patient aged 200; a \u201Chealthy\u201D ECG that flat-lines; a GAN image with six fingers; the same texture tile repeating across an image; synthetic bills whose amounts all end in .00
Integrate into the pipeline
  • Apply augmentation only to the training set; validation and test stay untouched
  • Document the lineage of every generated sample
Ensure reproducibility
  • Log parameters, seeds and methods
  • Version-control the synthetic datasets
  • Maintain metadata for compliance and audit

Transform (e) — Feature engineering

Phase III · stage 8 — FIT on train, APPLY elsewhere

Every step here is stateful: its parameters are computed from the ENTIRE training dataset at once (a mean over all rows, a category list over all rows) — not from any single row. The rule for the whole stage — and for every exam question about it: fitted on training, applied to validation, test and production with the training parameters, refitted at retraining.

Imputation — handle missing fields (fitted)
Fitted treatments (AFTER the split; fit on train, then APPLY the stored values to validation & test too):
  • Handle missing values (drop, impute, forward/backfill) — the fill VALUE (median/mean/most-frequent) is learned, so it is computed on train only. It IS then applied to validation and test: their missing cells are filled using the train-learned value. Why apply but not fit? Validation/test must travel the exact pipeline production data will travel — but if they also TAUGHT the pipeline, the exam would be leaking into the study notes.
  • Outlier treatment — two separate parts:
    • Part 1 · Detection (where the fitted rule lives): the thresholds that define “too extreme” (z-score limits, IQR fences) are computed from the training data; the SAME fences are then applied to validation and test.
    • Part 2 · Treatment (what to do with each flagged value): investigate first — is it a real value or an error? A ₹9,00,000 bill may be a typo, or a real surgery. If it is an error → correct it or treat as missing (impute). If it is real but extreme → cap/winsorize or log-transform to soften its pull. If it is real and MEANINGFUL (fraud!) → keep it and use robust models. Never silently delete rare real events.
  • Choose the imputer by the column: mean for roughly symmetric numerics · median for skewed columns with outliers (mean on skewed income inflates values) · mode (most frequent) for categories · forward/backward fill or interpolation for time series (trap: backward fill in a live stream reads the future → leakage) · algorithmic imputation (KNN, MICE, model-based) when gaps depend on other columns.
Create new, meaningful features from raw data to improve model performance
  • Domain-driven derivations — sort each new feature by what it READS (this is a different sorting from the two buckets of stage 13 — there we sorted cleaning fixes; here we sort NEW features — but the underlying rule is the same one):
    • Row-wise (reads one row → safe BEFORE the split): ratios (readmission risk = prior admissions ÷ age), days-since-last-discharge — each reads columns of its OWN row only, so no validation/test information can leak through it. So yes: this part of feature engineering is allowed to run before the split; only the fitted parts below must wait.
    • Aggregated (fitted — after the split, computed on train only): “average lab value per doctor”, “patient’s historical mean” — these read ACROSS rows, so computed on all data they would absorb validation/test rows. Compute the averages from train; apply the stored averages to the other sets.
  • Encoding categorical variables — the method per column is CHOSEN here, and the encoding is APPLIED once, below in this same stage (the encoding cards that follow). No double encoding — design and execution are two moments of one stage-18 activity.
  • Text features: TF-IDF, embeddings, NLP extraction from clinical notes — all three build a vocabulary/model from data → fitted on train only, after the split
  • Interaction features — a new column built by COMBINING two existing ones, because sometimes the signal lives in the combination, not in either column alone: comorbidity × age (an 80-year-old with three conditions is far riskier than either fact suggests separately) · polynomial combinations (age², income × tenure).

Same word, two meanings — placed where each belongs in a real project: stage 13 · Cleanse did “format standardisation” — text/format hygiene (dates, units, casing), row-level, before the split. THIS step is statistical rescaling of numbers, and runs AFTER the split because the scaler is learned from data (fit on train only). One more sequencing note: scaling and encoding are siblings, not a sequence — scaling rescales the NUMERIC columns, encoding converts the CATEGORICAL columns into numbers; both are fitted on train after the split, and it does not matter which of the two you run first.

Decide the method by model type — then apply without leakage
  • Normalization (min-max scaling, values → [0,1]): for distance-based models (KNN, SVM, neural nets)
  • Standardization (z-score, mean = 0, variance = 1): for distribution-based models (linear/logistic regression, PCA)
  • Store fitted parameters (min, max, mean, std) from the training set; apply consistently across all subsets
  • Validation: check transformed distributions (histograms, boxplots); ensure scaling doesn't distort feature relationships; confirm no leakage (test set untouched during fitting)
  • Reproducibility & documentation: log scaler parameters · version-control transformations (MLflow, DVC, Git) · document which features were scaled, why, and how · ensure transformations are repeatable in production pipelines

Encoding is not only for high cardinality — EVERY categorical column must be encoded, because models only eat numbers; the table below covers all of them. The special case where the CHOICE really matters: high-cardinality categories — variables with a large number of unique values (e.g., pincode) → use target encoding with cross-validation (compresses the information into a single dense feature while explicitly preventing data leakage), not one-hot (one-hot creates a sparse — thinly scattered — high-dimensional matrix that triggers the curse of dimensionality, draining memory and degrading model performance).

All the encoding methods — what each is, when to choose it
MethodWhat it doesChoose it when
One-hotOne yes/no column per categoryFew categories (≤ ~15), no order between them (channel: SMS/app/web)
Label encodingEach category → an arbitrary integer (0,1,2…)Tree-based models only (trees don't read the numbers as sizes); never for linear/distance models
Ordinal encodingCategories → integers IN their natural orderA real order exists: mild < moderate < severe
Frequency / count encodingCategory → how often it appearsPopularity itself carries signal; quick baseline for many categories
Target encoding (+ cross-validation)Category → the answer-column's average for that categoryHigh-cardinality fields (pincode, doctor ID); must be fitted after the split, inside CV
EmbeddingsCategory → a short learned vector; similar categories end up closeVery many categories with hidden similarity (words, products, users); deep-learning settings
Why this matters
  • Memory: 20,000 pincodes one-hot = 20,000 columns of mostly zeros — RAM and storage drain for no signal.
  • Speed: every extra column slows training and inference.
  • Overfitting: a pincode seen 3 times gets its own column and the model memorizes those 3 rows instead of learning.
  • Accuracy: and yes — sparsity and the curse of dimensionality rise TOGETHER: every mostly-zero column one-hot adds is another dimension across which the same rows are spread thinner, so patterns dissolve and performance degrades. That coupling is exactly why one-hot on 20,000 pincodes hurts.
  • The fix in one line: target encoding keeps ONE dense, informative column; the cross-validation wrapper is what stops it peeking at the answer (leakage).

Encoding traps the course tests
  • One-hot for linear models: drop one column (drop="first") to avoid perfect multicollinearity.
  • Frequency/count encoding: counts must come from the TRAINING set — counts on the whole dataset leak test frequencies in.
  • Target/mean encoding: must be out-of-fold and smoothed — without OOF and smoothing on tiny categories the leakage is extreme.
Create, enrich, vectorise, select, reduce
  • Derived features — date parts, ratios, interactions, aggregates (rules from our step above apply: row-wise before the split, aggregated fitted on train). Trap: post-outcome information (“refund issued” predicting “will complain”) — the feature will not exist at prediction time.
  • External enrichment — join weather, demographics, metadata that EXIST at prediction time.
  • Vectorisation — this is where text finally stops being human-readable: tokenize (chop text into model-ready pieces — applying an existing pretrained tokenizer is deterministic, but building a NEW vocabulary, whether a BPE tokenizer’s word-list or a TF-IDF vocabulary, means learning the word-list from data → build it on train only), then map to embeddings/TF-IDF; images resized & cropped; audio sliced; and for RAG, chunk long documents just before embedding them. Identical logic at inference.
  • Target-driven feature selection — correlation, importance, L1: decided on the TRAINING set only (the domain-driven column drop already happened in stage 14).
  • Dimensionality reduction (PCA) — TRANSFORMS features into fewer components; it does not drop columns. Fitted on train.

GATE 2 · Validate & gate — go/no-go into model work

Decision gate · stage 9
The leakage audit — five types to hunt
  • 1 · Target leakage (post-event / look-ahead features) — a feature generated AFTER the target event: “refund issued” predicting “customer will complain”. The model looks perfect offline, useless live.
  • 2 · Pre-split transformation leak — statistics (mean, variance, max, encodings, PCA) computed on the whole dataset instead of the training split. The most common silent leak in notebooks.
  • 3 · Leaky IDs / indices / timestamps — administrative keys that correlate with the target (claim IDs issued in blocks per outcome).
  • 4 · Duplicate rows across sets — the same sample in training and test; dedup before the split, hash-check the sets here.
  • 5 · Group leakage — one person's rows spread across sets; the group split (stage 16) prevents it.
Distribution, bias & label-quality checks

  • Representation per group — balanced classes can still hide skewed demographics.
  • Label QA — inter-annotator agreement ≥ 0.8, spot checks, annotator confusion; good images with bad labels = bad data.
Validate preprocessing & transformation results
